# 撤销、重做与恢复

## 统一规则

所有已存版本的恢复都在当前分支追加提交。旧版本始终留在历史里，不移动分支回退、不删除提交，也不自动创建分支。Git 恢复只涉及获授权的追踪文件，图片、视频及其归档不在恢复范围内。

主 Agent 明确交接用户意图、目标版本及文件范围。日期或描述对应多个候选时先列出候选，由主 Agent 澄清，不猜测目标。

首次存档是基线。撤销目标为没有父提交的首次存档时，直接返回“没有可撤销的历史存档。”，不删除文件、不创建提交、不改变暂存区；“再撤销一步”到达基线时同样处理。这不影响之后将文档恢复到该基线版本。

操作前：
- 记录当前 HEAD，作为恢复前版本，明确将改变的文件及可能的删除；用户明确提出的恢复请求就是该范围的授权，不反复询问。
- 工作区和暂存区需没有未存档文档改动。若有，先返回主 Agent，由用户决定先存档还是取消本次恢复；不自动 stash，不顺带提交其他工作。
- 确认操作范围没有图片、视频或敏感配置；旧提交包含这类路径时只恢复获授权的文档路径，不用整仓覆盖将它们重新带入追踪。

## 三种动作

| 请求 | 行为 |
|---|---|
| 撤销某次保存 | 新增提交抵消那次保存的改动，其他历史保留 |
| 恢复某个版本 | 将指定文件或 Git 管理的项目内容恢复为目标快照，新增提交 |
| 重做刚才的撤销 | 新增提交逆转对应的撤销提交 |

“撤销刚才保存的版本”对应最近一次用户指定的存档，不把“撤销提交本身”误认为普通存档。“再撤销一步”需追溯尚未被撤销的上一个存档；对应不唯一时交主 Agent 澄清。通过下面的关联字段识别撤销、重做关系，不额外建立历史数据库。

## 撤销与重做

在干净状态下，对普通提交使用 `git revert --no-commit <save-sha>`，检查结果后提交，正文记录：

    Undo-of: <完整 save-sha>

重做使用 `git revert --no-commit <undo-sha>`，检查后提交，正文记录：

    Redo-of: <完整 undo-sha>

若撤销后已经继续编辑，重做需检查是否影响后续修改；不能不经核对就用旧快照覆盖当前文档。遇到合并提交、部分文件撤销需求或冲突，不猜父提交、不自动选边，交主 Agent 明确后按文件快照恢复或另行处理。

## 恢复快照

从仓库根目录操作，明确列出全部获授权路径：

    git restore --source=<target-sha> --staged --worktree -- <paths>

路径集合包括目标中要恢复的文件及当前版本中需要删除的文件。整项目恢复时取当前与目标追踪路径的并集，排除媒体、敏感文件和不属于请求的路径，再逐项传入；不要以扫描本地所有文件代替追踪范围。整项目恢复默认指项目内容，不回退当前 `.gitignore`、`.gitattributes` 等版本管理配置；用户专门要求恢复配置时仍需保留媒体排除策略。

核对内容后创建提交，正文记录：

    Source: <完整 target-sha>
    Before: <操作前完整 HEAD>

这会保留新增、删除等快照差异；不通过文本管道导出二进制文档。当前内容与目标一致时不创建空提交。

## 验证与中断

- 用来源版本和新提交的文件内容核对恢复结果；二进制文档核对 Git 对象内容一致性，必要时打开或渲染，不要求 Git 解释内部差异。
- 确认旧 HEAD 仍在当前历史中，提交范围正确，媒体未被追踪或移动。
- 当前操作若产生 revert 冲突，按 [conflicts.md](conflicts.md) 中止；不留下本次产生的半成品。
- 记录了原 HEAD 且操作前干净时，快照恢复在提交前失败，可仅对本次受影响路径从原 HEAD 恢复暂存区及工作区；提交后需要反向恢复时再新增提交，不删除已完成提交。

返回新提交、来源或对应提交、恢复前版本和可逆转它的说法。超出普通版本恢复的历史救援请求先只读检查并向主 Agent 报告，不自动改写历史。
