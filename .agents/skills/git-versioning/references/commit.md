# 保存阶段版本

## 检查交接信息

保存前必须取得：用户的保存授权、仓库与本阶段文件范围、本阶段修改及必要原因。修改原因由主 Agent 提供；没有额外原因时可明确说明“无额外原因”，子代理不得从差异猜测业务动机。

交接中的已知无关改动需保留。范围或原因缺失、与文件内容不符时，先向主 Agent 补齐；不要自行扩大范围，也不要在子代理里另起一轮用户沟通。

## 提交流程

普通存档不执行配置维护；不为补齐规范而修改 `.gitignore`、`.gitattributes` 或 AGENTS.md。这些文件只有本来就属于本次获授权任务时才处理。

1. 核对当前分支、HEAD、`git status --short`、工作区和暂存区的路径清单；先排除敏感文件再查看范围内的内容差异。遇到冲突或未完成操作先读 [conflicts.md](conflicts.md)。
2. 核对本阶段路径与具体改动。提交中只能包含本阶段修改及必要原因；不把历史遗留改动、其他任务或用户的个人笔记顺带提交。同一文件混有其他阶段修改时，只暂存可区分的本阶段改动；二进制文件或无法可靠区分的内容退回主 Agent 确认。
3. 排除图片、视频、缓存、临时文件、密钥及凭据。本阶段涉及媒体时，将 [setup.md](setup.md) 的命名与归档约定交回主 Agent 处理，待相关文档引用确定后再保存文档版本。二进制文档以主 Agent 的变更说明和实际文件核验为依据，不凭“binary files differ”编造内容描述。
4. 按明确路径或选定差异暂存；不使用 `git add .` 或 `git add -A`。已有无关暂存内容时，不清空暂存区：整份路径均属于本阶段时可以使用 `git commit --only -- <paths>`；部分暂存场景使用隔离索引等可靠方式，无法保证时停止并报告主 Agent。注意 `--only` 会提交指定文件的工作区内容，不能用它隔离同一文件内的无关改动。
5. 创建提交前检查实际将提交的路径及差异。没有变化时说明无需新版本，不创建空提交。创建后核对 `git show --stat HEAD` 和状态，确认无关文件的内容及原有暂存状态未变。

## 提交信息

一次提交对应一个用户可理解的阶段，可包含多个相关文件。使用项目工作语言，默认用用户语言。

标题用一行简短说明完成了什么，不强制类型前缀、显示列数或按文件拆分。必要时正文只记录主 Agent 提供的原因，不写无关任务过程、聊天记录、推测或密钥。

    调整活动方案受众为新入职员工

    原因：先在公司内部试点

恢复类提交同样使用简短标题，并按 [recovery.md](recovery.md) 记录准确的来源或对应提交编号。

## 返回主 Agent

返回提交编号、标题、本阶段文件、必要原因及剩余无关改动。后续存档可附上“撤销刚才保存的版本”这样的自然语言说法；首次存档只说明已建立基线，不提供可撤销该基线的提示。保存阶段版本不要求整个工作区干净。
